# Cross-repo impact review

Single-repo tools (`graph_get_references`, `graph_impact_analysis`) can't see other repos, so "no
callers found" in this repo proves nothing about a route, message, or event that crosses a repo
boundary. This skill is the checklist for those changes.

## 1. Find which cross-repo surface the change touches

From the diff, list anything that is part of an inter-repo contract:

- **Route** — a controller action / route attribute, its path, HTTP verb, or request/response shape.
- **Message** — a Service Bus message contract class, or a consumer/publisher of one.
- **SignalR event** — a hub method or event name.
- **Generated client call** — an NSwag/HttpClient call into another service (the *caller* side).

If the diff touches none of these, this skill doesn't apply.

## 2. Look up who is on the other side

Use whichever source is available, in this order.

**A. Live workspace tools** (server `rs-graph-workspace`) — most current:
`graph_workspace_route_consumers`, `graph_workspace_message_consumers`,
`graph_workspace_signal_consumers`, taking the symbol id from this repo's own graph
(`graph_get_route_map`, or `graph_search_symbol` with `kind: "MessageContract"` / `"HubEvent"`).
If one returns empty, call `graph_workspace_status` first — empty can mean a repo isn't indexed yet.

**B. `CROSS_REPO_MANIFEST.json` / `.md` at the repo root** — the only option when just this repo is
checked out. Find the entry by its key:

| Surface | Key | Section |
| --- | --- | --- |
| Route (defined here) | `xrepo:route:<path>` — lower-cased, no leading/trailing slash, every `{param}` written as `{}` (matched by path *shape*, not parameter name or verb), e.g. `xrepo:route:api/v1/vessel/{}` | `routesDefined` → `counterparts` are the callers in other repos |
| Route (called here) | same key | `routesCalled` → `counterparts` are the producers |
| Message | `xrepo:message:<TypeName>` | `messagesPublished` / `messagesConsumed` |
| SignalR event | `xrepo:signal:<name>` | `signalsPublished` / `signalsConsumed` |

Each counterpart gives `repo`, the symbol in that repo, and its `role`.

**C. Neither available** — say so plainly. Don't treat that as "no consumers".

## 3. Judge the change

- **Removing or renaming** a route/message/event that has counterparts: breaking. Name each affected
  repo and symbol.
- **Changing a route's path shape** (adding/removing segments or parameters): same as removing the
  old one — every listed caller breaks.
- **Changing a message contract's or response's fields**: list the consumers/callers; flag removed or
  retyped fields and new *required* fields as breaking for them.
- **Adding** a route/message/event: no existing counterparts; note it for completeness only.
- **Verb changes** are not visible in the manifest (route keys ignore the verb); if the diff changes
  a verb, say that callers' verbs can't be checked from here.

## 4. Be honest about what the evidence can't show

- The manifest is generated by `rs-graph generate-manifest` / `index-workspace` and may be **stale**:
  check `generatedAt` against how recently the other repos changed. `watch-workspace` keeps it fresh
  locally, but a committed copy is only as new as its last commit.
- It only knows repos in the workspace and only calls rs-graph can detect (generated clients, plain
  `HttpClient`/Angular `HttpClient` with string or interpolated URLs, MassTransit/Service Bus, SignalR).
  A caller built from a concatenated or variable URL, or in a repo outside the workspace, won't be there.
- So report **"no known consumers (manifest as of `<generatedAt>`)"**, never "no consumers".
- If the change is breaking and the evidence is thin, ask the author to confirm with the owning team
  rather than approving.

## 5. Report

Lead with the verdict (breaking / non-breaking / can't tell), then list affected repos and symbols,
then the evidence used (live tools vs manifest, with its `generatedAt`).
